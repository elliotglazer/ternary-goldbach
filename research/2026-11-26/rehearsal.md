# Replaying ternary Goldbach on AWS and under Palomar

On 26 November 2026, stock Lean 4.35.0 on Linux compiled the combined theorem that every odd natural number greater than five is a sum of three primes. A fresh Lean process imported the solution and reported exactly `propext`, `Classical.choice` and `Quot.sound`. In the private rehearsal, Palomar’s stock verifier then built the candidate under its resource limits and exported the proof for independent checking. [Published Lean result](https://github.com/elliotglazer/ternary-goldbach/tree/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/joined-theorem-3ca2fcf7) · [Protected checkpoint](evidence/performance-1240.json)

## Reading a stopped build

The first remote run illustrated how little a machine’s state says about a proof. The launch returned successfully. A console snapshot showed Ubuntu booting, the management agent starting and the shutdown timer armed. A later request for logs failed because the instance had stopped. The retained console finally reported `challenge-build failed with 1`. The runner had written a receipt before the guest shut down, and the evidence volume was still attached. A boot message could establish that the machine had started. Only the stage log could explain why the challenge had failed. [Source replay driver](https://github.com/elliotglazer/ternary-goldbach/blob/1cb80db0cf07ee59d6e9dd27030c921f90595d14/verification/community-grh/grh_source.py)

Subsequent runs recorded the requested Lean root, source commit and tree, exit code, elapsed time and hash of the full build log. We kept the original run directory when a job failed or reached its deadline. A retry wrote a new result. That mattered when a single Lake invocation had completed hundreds of modules and then encountered an error in an unrelated branch. The completed modules were potentially reusable even though the requested theorem remained open. [Warm build driver](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/warm-main/warm_main.py) · [Recorded failed build](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/warm-main/result-4d574858.json)

## Carrying proof objects across revisions

The large development had two independently buildable roots. `Main` supplied the RH and Dirichlet GRH declarations. `CompletedFiniteRows` supplied a conditional ternary theorem, including the binary computation and four analytic profile groups. The latter reached every even number from 4 through **564,386,325,504**. Its ternary argument uses the slightly smaller endpoint **564,383,557,524**. Splitting the build here let a repair in algebraic geometry proceed without restarting the binary calculation. [Finite theorem and endpoints](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/finite-terminal-22f442fa/README.md) · [Final bridge](https://github.com/elliotglazer/ternary-goldbach/blob/3ca2fcf7e3dd1897ff242d8e482aa7f82abe263b/CompletedGoldbach.lean)

Before reusing a module, the diagnostic runner checked its successful build record, tracked source bytes, Lake trace and compiled output hashes. It checked which versions of the imported modules had produced that object. A changed source or parent invalidated the dependent result. If a worker stopped before writing its terminal receipt, only modules completed in an independently authenticated log prefix could qualify. The interrupted finite run contributed 454 completed modules by this rule. Separate controls exercised a changed input and an interrupted job. [Interrupted-run control](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/warm-main/sealed-finite-recovery/interrupted-control.json) · [Timeout controls](https://github.com/elliotglazer/ternary-goldbach/tree/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/warm-main/timed-roots)

One GRH retry illustrates the value of keeping these records. It admitted 354 earlier modules and compared the next build against 16 previously observed failures. The new log showed exactly which repairs had reached a real compile and which errors remained. On the last two GRH runs, the first reused 738 modules, built 43 more and stopped at `New.Rows.Separation`. The repaired successor reused 781 and built the last 13. This was also why we declined to forecast completion by dividing the Lake progress counter by its total. One remaining module could block several short dependents, and Lake’s counter included work outside the 794-module project root. [Earlier 16-failure comparison](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/warm-main/prior-16-comparison.json) · [Final GRH source](https://github.com/elliotglazer/ternary-goldbach/blob/3ca2fcf7e3dd1897ff242d8e482aa7f82abe263b/CompactGRH/src/New/Rows/Separation.lean)

## Separating proof defects from resource limits

The source conversion exposed real elaboration failures. For example, two different modules that used a continuous-cocycle construction failed with the same diagnostic about an automatic proof argument. Supplying that default on the declarations which consumed it fixed both callers. Elsewhere Lean needed a matrix or polynomial supplied explicitly where the upstream tactic had left it to inference. We tested prospective edits on the original declaration and its actual imports whenever those imports were available. A successful small example narrowed the diagnosis. A successful compile of the complete consumer established that the fix worked there. [Continuous-cocycle declarations](https://github.com/elliotglazer/ternary-goldbach/blob/3ca2fcf7e3dd1897ff242d8e482aa7f82abe263b/CompactGRH/src/Lib/ClassField/GaloisCohomology/ContinuousCocycles.lean) · [A downstream matrix witness](https://github.com/elliotglazer/ternary-goldbach/blob/3ca2fcf7e3dd1897ff242d8e482aa7f82abe263b/CompactGRH/src/New/Filling/PoincareSeries.lean)

The finite calculations had a different failure mode. Two concurrent Lean frontends each reached about 24 GiB of resident memory. After roughly 17 minutes each had accumulated about 375 seconds of system CPU and only 15 seconds of user CPU. The memory controller recorded heavy reclaim. Those figures changed our interpretation of the apparent stall. Adding more concurrent workers to the same memory budget would have exacerbated it. We tried synchronous elaboration in the affected interval files. We also marked large proof-only bitmap constants `noncomputable` so C generation could omit enormous decimal literals. The interval statements, row witnesses and kernel checks still ran. The eventual finite source job reused 525 modules, built 207 and finished in 22 minutes 39 seconds. That is a measured warm run for the last 207 modules. [Bitmap change](https://github.com/elliotglazer/ternary-goldbach/commit/b6535e79fde64adc5288e02ad3393bd1eca94631) · [Synchronous-elaboration change](https://github.com/elliotglazer/ternary-goldbach/commit/dafa3e64289998b784aca99ec8fb491ddaac5362) · [Finite terminal receipt](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/finite-terminal-22f442fa/receipt.json)

One experiment measured the cost of adding work to a shared proof. After Lean had loaded the common bitmap and primorial certificate, the stock kernel checked a second adjacent tile and joined it to the first in 0.594 to 0.625 CPU seconds across three trials. Each tile covered 33,554,432 even inputs. A separate portable replay took 1.047 CPU seconds for the same step. This measurement excludes the initial imports, export generation and the external checkers. Charging an entire standalone kernel run to every tile would repeatedly count the common certificate. [Paired-tile experiment](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/paired-product-tile-kernel/README.md)

## What the 37-second result established

The finite root had passed on commit `cb1dffe1`. The GRH root passed on `3ca2fcf7`. Before combining their outputs we checked that all **732 finite source files** and their project imports were identical at both revisions. The toolchain, Lake configuration, package manifest, final bridge, solution, challenge and comparator configuration also agreed. The join checked **1,526 source traces** and **7,630 compiled-file hashes**. It reproduced the fingerprints of direct imports before passing the two sets of objects to Lean. [Public join evidence](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/joined-theorem-3ca2fcf7/evidence.json)

Lean compiled `CompletedGoldbach` in 26.648 seconds. This is the step that applies the unconditional RH and GRH declarations to the remaining hypotheses. It compiled `GoldbachSolution` in 2.806 seconds. A fresh process then imported the solution, printed its type and listed its axioms in another 2.806 seconds. Including the input checks, the join took **37.321 seconds**. The result covers every odd natural number greater than five. Those 37 seconds depended on both earlier source builds. [Verbatim Lean output](https://github.com/elliotglazer/ternary-goldbach/blob/c6368decde84d4be04943117a2bfef991f9b1831/verification/community-grh/compact/joined-theorem-3ca2fcf7/fresh-import.log) · [Published solution](https://github.com/elliotglazer/ternary-goldbach/blob/3ca2fcf7e3dd1897ff242d8e482aa7f82abe263b/GoldbachSolution.lean)

## The protected rehearsal

Palomar compares two independently built declarations. The challenge imports only Mathlib’s natural-prime definitions and parity, and contains a trusted statement stub. The solution imports the completed proof. The verifier builds the two sides separately, produces one challenge export and one solution export, compares their declarations and permitted axioms, and runs its kernel checks on the solution export. This exercises work that a fresh Lean import does not measure. It also explains why a fast elaboration time by itself cannot establish that the submission fits the protected clock. [Challenge](https://github.com/elliotglazer/ternary-goldbach/blob/3ca2fcf7e3dd1897ff242d8e482aa7f82abe263b/GoldbachChallenge.lean) · [Comparator configuration](https://github.com/elliotglazer/ternary-goldbach/blob/3ca2fcf7e3dd1897ff242d8e482aa7f82abe263b/comparator.json) · [Current stock verifier](https://github.com/PalomarRegistry/PalomarSubmission/blob/046554302064b2c83c2b924bea6db87fc5900c68/scripts/verify_submission.py)

An early protected attempt passed the resource probes and source intake, then exited 127 in the initial confinement check. Python could start on the host. Inside Bubblewrap it could not find `libpython3.11.so.1.0`. The copied virtual-environment executable retained a library search path pointing to the base Python installation. The verifier grants read access to the prefix containing the *resolved executable*. Copying the executable made it select the virtual environment and leave the base runtime outside the sandbox. [Verifier used in the first attempt](https://github.com/PalomarRegistry/PalomarSubmission/blob/14aa8d6b3c2f14a8540605e37144560b9a00e7e7/scripts/verify_submission.py#L6019-L6038)

The current published workflow selected Python 3.11.18. We ran the stock Bubblewrap command and syscall filter with three interpreter layouts. The original copied Python 3.11.10 reproduced exit 127. Copying the new 3.11.18 binary reproduced it again. Using the ordinary linked 3.11.18 virtual environment succeeded and loaded the standard library and OpenSSL. With a symbolic link, the existing verifier resolves the interpreter to its intended versioned installation and includes that prefix itself. The candidate proof, verifier source, sandbox policy and resource ceilings stayed fixed for the layout comparison. [Pinned workflow](https://github.com/PalomarRegistry/PalomarSubmission/blob/046554302064b2c83c2b924bea6db87fc5900c68/.github/workflows/submission.yml#L148-L163) · [Current prefix selection](https://github.com/PalomarRegistry/PalomarSubmission/blob/046554302064b2c83c2b924bea6db87fc5900c68/scripts/verify_submission.py#L6076-L6097)

At **12:40:01 UTC**, the new protected run had passed initial confinement and reached `solution-build`. The snapshot counted **655 completed project traces** and **21 active Lean processes**. The memory controller charged **58.6 GiB** to the aggregate group against a 64 GiB limit. It reported zero swap use and zero out-of-memory kills. A trace count cannot estimate time remaining without the costs and dependency order of the remaining modules. This checkpoint established that the protected build was running under the intended envelope. The build continued for another 95 minutes after this checkpoint. [12:40 protected performance sample](evidence/performance-1240.json)

The cold build finished successfully in 1 h 44 min 26 s. The build cgroup used 13.97 core-hours and peaked at 62.45 GiB. The verifier then spent 32 min 26 s exporting the solution. At 14:47 UTC it passed the 6,079,160,562-byte solution export and the 1,434,686-byte challenge export to the comparator. Its report had no kernel verdict at that point.
