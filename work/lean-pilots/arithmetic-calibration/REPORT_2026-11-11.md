# Lean 4.35 signed-dyadic arithmetic calibration

Frozen 2026-11-11. The four synthetic arithmetic fixtures passed actual Lean kernel checking at trust level zero. Both deliberately corrupted claims were rejected for every fixture. This measures one unoptimized proof representation; it is not a complete spectral pilot, an optimal Lean implementation, or a conversion rate from the separate MM0 byte-operation model.

## Checked mathematical object

At precision p, S=2^p. Integer coordinates a,b,c,d represent two complex dyadic centers at grid 2^-p. The circuit computes

    t=c(a+b), u=b(c+d), v=a(d-c), rr=t-u, ii=t+v.

General proved integer identities identify rr=ac-bd and ii=ad+bc. For each coordinate n, the supplied output q and remainder r satisfy

    n+S/2=q*S+r, 0<=r<S,
    -S<=2*(n-q*S)<S.

This is nearest rounding with ties toward positive infinity, including negative half ties. The 100-bit tie fixture has both a positive real half tie and a negative imaginary half tie. The other three fixtures are the same fixed nontrivial signed-input pattern at p=74,100,120. No roots, function values, prime candidates or zero data were generated.

Each fixture has 21 theorem declarations. The final theorem includes actual input, coefficient-cache, raw-intermediate and output bounds, both exact product identities, and both rounded residual intervals. Additional concrete bounds cover the data presum, coefficient squared norm, shifted outputs, and both raw sides of each rounding witness. They are proved from actual integer literals, not inferred from acceptance of a narrow residual. The coefficient norm is at most one for these fixtures; uncertain coefficient enclosures and analytic complex-error transport are outside this calibration. The semantic Real/Complex interpretation of the scaled integer inequalities is described here but is not a separate formal Real embedding theorem in this pilot.

Conservative signed capacities (sign included) and corresponding whole-byte capacities are:

| p | input | coefficient | raw product/round expression | rounded output |
|---:|---:|---:|---:|---:|
|74|85 bits / 11 bytes|76 / 10|161 / 21|86 / 11|
|100|111 / 14|102 / 13|213 / 27|112 / 14|
|120|131 / 17|122 / 16|253 / 32|132 / 17|

The data presum and cached coefficient sums have their explicitly proved larger ranges in the source. These capacities describe mathematical integers, not a custom fixed-width machine implementation. The saved summary also records actual operand bit lengths. The nominal circuit has three real products, but the proof workload includes additional norm/range computations, output-times-S witnesses, equality normalization, and repeated occurrences in types. It must not be priced as precisely three isolated kernel multiplications.

## Acceptance and measurement method

Direct executable: `C:/Users/glaze/.elan/toolchains/leanprover--lean4---v4.35.0/bin/lean.exe`, version 4.35.0, commit eb6cafb7290e8bd5f2937522d8d804f58f02bafc. Command flags were `-t0 -j1 -M1024 -o ...`. There were no dependency builds, heartbeat overrides, `native_decide`, `sorry`, or custom axioms. Imports are `Lean.Elab.Command` and `Lean.Elab.Tactic.Omega`; Mathlib was not imported. The observed default kernel heartbeat parameter was 200000000 and recursion depth 512.

Concrete arithmetic facts use ordinary `by decide`; the three shared generic integer lemmas use ordinary rewriting and omega. The axiom audit reports exactly `[propext, Classical.choice, Quot.sound]` for each final certificate. Thus the pilot is not claimed axiom-free; no `sorryAx` or problem-specific axiom is present.

After elaboration, the harness extracts the actual theorem expressions. It renames all 21 fixture declarations to fresh names, rewrites their dependencies, and rejects any surviving reference to the original `Fixture` namespace. It then calls checked `Kernel.Environment.addDeclCore` on every declaration in dependency order. Each repetition starts from the same base kernel environment, so fresh declarations do not accumulate between repetitions. Shared generic lemmas and imported library declarations remain checked dependencies in that base. One valid warmup precedes each timed bundle.

The corrupted controls retain the genuine proof but change the first multiplication's claimed result, or the real rounding witness's claimed right side, by one. Both are actually submitted to the kernel and rejected. They are not merely compared in Python. The fixed metadata summarizer independently checks the supplied integer identities and tie inequalities, but that is diagnostic evidence only; Lean acceptance is the proof check.

**Kernel replay time excludes tactic elaboration and proof-pool construction.** The separately recorded pool time (7.5–10.4 ms in the final runs) is expression renaming/binding, not proof generation. Whole-process time includes imports, source elaboration and its inline kernel checks, pool construction, all replay experiments, controls, and output serialization. No clean standalone tactic-generation timing was measured.

Each final run accepts 8,400 timed declarations in the full loops and another 8,400 in the part loops, plus untimed warmups/prerequisites. ## Permitted interpretation

The measured reference is a complete concrete 21-declaration arithmetic certificate with replayed local auxiliaries. It gives evidence that this representation can be generated, ordinarily checked, audited, and rejected when corrupted at the stated widths. It does not fix the best batching granularity, equality normal form, range-proof sharing, certificate encoding, or proof-generation strategy. A batched conjunction or different numeral proof architecture can materially change overhead; no such speedup has been measured here.

A production estimate must separately state any assumed mapping from its multiplication/addition inventory to this reference bundle. In particular, neither the MM0 byte-operation counts nor a count of three complex-gate real products has an established empirical conversion to these milliseconds. Generation, analytic functions, coefficient/cache uncertainty, phase and interpolation, successful signs/completeness, principal verification, binary coverage, and shared library costs remain separate. No backend ranking or final core-hour forecast follows from this pilot alone.
