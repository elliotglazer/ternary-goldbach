## 1. Main conclusion and remaining capability gate

A retained process handle permits a **conditional post-exit memory query protocol**. It does not guarantee that a memory query will succeed after every exit. Use the original handle returned at creation, wait for signaled process termination, then require a fresh successful `GetProcessMemoryInfo` call before releasing the handle. Interpret a successful result according to the documented `PeakWorkingSetSize` meaning. Reject absent, zero, malformed, or inconsistent results; never substitute the last live sample or a different memory metric.

The documentation inspected defines the counter as peak working-set bytes and explains process-object lifetime, but does not explicitly promise post-exit query availability or separately specify historical-counter retention after termination. Thus this note does not claim that availability has been established on the present host. Before relying on the protocol, require a separately authorized benign capability preflight of the exact supervisor/API binding on the actual Windows/Python versions. That would test availability and catch implementation/ABI mistakes, not prove a universal OS theorem. No such preflight is authorized or run by this note.

Under the documented successful-query interpretation, a successful final query covers the process whose lifetime has ended, including serialization and shutdown. The plausibility tests below are additional corruption checks, not an independent proof of the kernel's counter implementation. If the API fails or the post-exit interpretation cannot be accepted for the chosen platform, the unchanged scientific spec requires `INCOMPLETE_TELEMETRY`. There is no fallback PASS based on polling.

## 2. What the APIs actually establish

`GetProcessMemoryInfo` takes a process handle with query access and returns a Boolean success indicator plus memory counters. The counters distinguish working set from commit; use `PeakWorkingSetSize`, measured in bytes. Declare the native signatures and structure layout explicitly. These claims follow from the [function documentation](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo) and [PROCESS_MEMORY_COUNTERS definition](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters).

When a process terminates, its process object becomes signaled and its exit code is set. An external open handle keeps the underlying object valid. This supports waiting and retaining identity through exit; it is not, by itself, a guarantee that every query against that object remains available. Terminating a parent also does not automatically terminate its descendants. See [Terminating a Process](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process).

`TerminateProcess` is asynchronous when invoked externally. Pending I/O may delay final termination. A successful call is not an observed exit; wait on the process handle afterward. Record the termination request and the eventual signaled state separately. These are explicit limitations in the [termination API](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess).

Job accounting is useful for ownership and process counts. `TotalProcesses` includes terminated processes and even failed associations caused by limits. `ActiveProcesses` can remain nonzero until relevant references are released, so do not require it to be zero while intentionally retaining the process handle. The [basic job accounting definition](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information) documents both points.

`PeakProcessMemoryUsed` in extended job information belongs to the job's committed-memory accounting. It is not an interchangeable spelling of peak working set, which includes shared resident pages. Neither it nor `PeakPagefileUsage` can satisfy the selected working-set gate. See [extended job limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) and [process working set](https://learn.microsoft.com/en-us/windows/win32/procthread/process-working-set).

This proposal does not add a hard working-set limit. Microsoft separately documents a hard-maximum flag in [SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex), but configuring it would be a different operational choice and still would not manufacture a measured historical maximum. The accepted spec already distinguishes breach detection from physical prevention of every transient overshoot.

## 3. Exact attempt and process identity

Before launch, freeze a small authorization record containing the scientific specification, code and input hashes; exact executable, arguments, working directory and environment; role; time/memory/output caps; a new attempt identifier and exclusive output locations; and the supervisor version/hash and selected memory-query policy. Reserve the attempt marker and completion-record space exclusively. No existing output or attempt marker may be overwritten or reused. A failed launch is recorded, not silently retried.

Use an explicit executable and argument list, no shell wrapper. Launch without a visible console window. Retain the original process handle throughout monitoring, wait, final queries and sealing; a PID is supplementary metadata, not sufficient identity because PIDs can be reused. Record creation/exit times from `GetProcessTimes` as corroborating metadata. Its [documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) explicitly supplies an exit time only after exit. Do not confuse user/kernel CPU totals with elapsed wall time.

For a race-free single-process job setup, a practical Windows implementation can create the evaluator suspended, retain its primary thread handle, assign it to a fresh job with active-process limit one, no breakaway permission and kill-on-last-job-handle-close, verify the job configuration, then resume the primary thread exactly once. If setup fails, terminate that suspended attempt and record failure; do not resume outside supervision. This is a design option for the later supervisor review, not code prepared here. [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) describes suspended creation, nested-job constraints, and default child association. The relevant count and cleanup flags are in [basic job limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).

The source audit must independently confirm no subprocess/delegated-worker path. Job accounting should end with `TotalProcesses=1` and no limit-terminated processes for a normal success. A different count makes the single-process tree claim false or unproved and rejects the attempt. Job completion-port notifications are supplementary; their absence does not prove that no event occurred, because most such notifications are not guaranteed. This is supervision of reviewed code, not a sandbox against malicious same-user code. Even the documented child-process restriction attribute has a privileged-process-handle caveat. ## 4. External elapsed-time protocol

Start an integer monotonic clock immediately before the native process-creation call. This includes creation, suspended setup, imports, all computation, serialization, flushing and evaluator shutdown. Never start the acceptance timer after `Popen`, after imports, or after a result has been computed. The observed signaled-exit time minus this start is a conservative launch-to-exit upper bound.

An external monitor uses short waits and recomputes the absolute remaining deadline. A frozen interval such as 20 milliseconds is a polling choice, not a promise about scheduler latency. On time expiry or another breach, mark the attempt irreversibly failed, request process/job termination, and wait for actual termination. A later exit code zero or valid payload cannot reverse that failure. If termination remains pending, retain `INCOMPLETE_TERMINATION`; never claim the deadline was met merely because the kill request was sent.

Use `perf_counter_ns`/`monotonic_ns` differences and record the implementation. Python documents the Windows monotonic clock's QPC basis; its performance counter includes elapsed sleep. Native wait timeouts on modern Windows exclude low-power-state time, so a single fixed `WaitForSingleObject` timeout must not be the only elapsed-time check. Recheck the monotonic deadline after every wait, including a signaled return. See [Python time](https://docs.python.org/3.14/library/time.html) and [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).

For simple fail-closed acceptance, require observed exit before the deadline. If the supervisor is descheduled and observes a timely child exit only after the deadline, this conservative protocol rejects; it does not infer an earlier monotonic exit timestamp from a wall-clock conversion. Record OS timestamps separately. Timing of post-exit supervisor hashing/sealing is separate and bounded operational work, not extra evaluator execution time.

A general Windows process-creation call and asynchronous termination are not hard real-time operations. The observer cannot guarantee physical stop at exactly 180 or 300 seconds under arbitrary OS stalls. It can enforce the acceptance deadline and request stop when scheduled. If process creation itself returns after the deadline, reject and stop the new attempt before computation resumes. Python's [subprocess documentation](https://docs.python.org/3.14/library/subprocess.html) explicitly warns that process creation may not be interruptible by its timeout. This is a limitation to report, not a reason to accept an overrun or replace the external monitor with an internal timer.

## 5. Lifetime peak-working-set gate

The supervisor owns a handle with synchronization, query and termination access, and queries OS peak working set while the process is live. Retain the raw returned counters, query timestamp, success/error information and the maximum observed OS peak, with bounded log volume. These are samples of an OS-maintained cumulative peak, not samples of current working set alone. Any observed peak above 536,870,912 bytes immediately invalidates the attempt and requests stop.

After the process handle becomes signaled, and before closing it:

1. Read and record the final exit code. Normal success requires zero and no previous failure flag.
2. Make a fresh memory query through the same retained handle into a newly initialized structure. Check native success, expected structure layout, and fields in bytes. Do not reuse a prior buffer after failure.
3. Require positive `PeakWorkingSetSize`, at least every earlier successful OS-peak observation, at least the simultaneously reported current working set, and at most 536,870,912. Zero, regression or malformed telemetry is `INCOMPLETE_TELEMETRY`. These checks detect some failures; they cannot independently prove OS correctness.
4. Record the query as post-signaled-exit, with API name/version, structure type/size, Windows build and raw counters. Missing post-exit data never becomes a “complete” peak by taking the maximum of polls.

On x64 the base `PROCESS_MEMORY_COUNTERS` layout contains two DWORDs followed by eight SIZE_T fields, giving 72 bytes. Its EX version adds PrivateUsage. Use `ctypes.c_size_t` for SIZE_T and a pointer-sized HANDLE; explicitly set `argtypes`, `restype` and last-error handling. An accidentally truncated handle or a 32-bit size field can yield meaningless apparent success. The later static review should check ABI assumptions and the benign preflight should exercise them.

The acceptance interpretation is conditional on the API's successful-query semantics applying to this retained terminated-process object. The reviewed docs do not establish universal post-exit availability. The preflight should compare a controlled live peak with the fresh post-exit value, include an allocate-touch-release phase and late serialization-like allocation, and check repeatable retention after exit. It should also exercise timeout and failed-query reporting on harmless processes. Such tests are proposed only; none ran here and none is authorized by this note. They support the selected platform path, not a guarantee for every Windows build.

## 6. Output budget, publication and completion seal

The 64 MiB budget is per attempt over all newly retained output: candidate, pending stream, checkpoints, stdout/stderr logs, attempt metadata and final completion record. Input artifacts already frozen before the attempt are separate. Reserve a bounded completion/failure-record allowance before permitting payload writes. Every writer must check aggregate remaining allowance, not a 64 MiB cap independently for each file. Do not retain both a complete pending snapshot and its complete final copy; rename the one owned stream or publish a small seal referring to it.

Drain output with bounded buffers; unbounded `communicate()` capture or a full in-memory log is inappropriate. The supervisor may use reader threads, but no numerical child workers. Byte accounting uses physical file lengths/raw UTF-8 bytes, not character count or pre-newline-translation size. On an attempted overrun, stop and preserve only the bounded partial files plus the reserved failure record. Never delete or overwrite unrelated files, and do not discard an inconvenient checkpoint merely to disguise an aggregate breach.

The evaluator's own PASS means candidate-complete only. It must serialize and flush all data and its final hash-bound message, then exit. It cannot attest to its own future full lifetime. The supervisor seals success only after signaled exit, normal status, final memory gate, complete process accounting, actual aggregate file-size checks and final file hashing. With no child writers and the evaluator exited, the retained candidate is stable under the intended isolated-attempt model. Unknown writers or file mutation reject.

The exclusive completion record contains the authorization/attempt/code/input hashes; original PID plus creation-time identity; start, observed-exit and deadline times; exit code and termination-request history; final post-exit memory-query status/raw peak and largest live peak; job process count; physical sizes and hashes of every retained file; candidate final-message binding; aggregate bytes and reserved-space accounting; and an explicit final status. Record the completion record's own hash in the coordinator's final console or external handoff. It cannot contain its own completed hash without a separate convention. Reject any mismatch between final console, seal and payload.

The supervisor seal is independently created after exit and is not evidence that the payload's mathematical claims are true. Full numerical/schema verification remains a separate gate. Conversely a mathematically valid payload with missing lifecycle evidence remains incomplete operationally.
